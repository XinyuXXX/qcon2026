1.1QUALITY
BRAKE

微软 Copilot：从早期提效到质量刹车

质量复盘

定位｜official 确认讲者为李榕（微软 CoreAI 软件开发经理）。这是商业软件团队的质量复盘，重心转向 Spec、Design、证据链、共享记忆与人才成长。

展开 / 收起技术档案

核心要点

  • 早期提效随后暴露质量问题。official 主证“提速 → Bug、投诉与返工增加 → 全员同意暂停新功能开发，集中修 Bug、恢复稳定性”。GitHub issue assign、市场差评、escalation、企业退订与“内部架构调整”仅为 recording-only 补充。
  • Sign-off 是证据链，不是一句“人负责”。人先批准设计；独立 Agent 只读 diff、还原实现思路并对照已批准设计；人再结合设计差异与测试证据作最终判断。符合设计 ≠ 设计正确。
  • 速度释放以质量和架构控制为前提。AI 可由 Spec 生成测试，并依据 call chain 选择测试子集做快速验证；资深工程师仍需检查 PR 的架构偏移。测试子集用于快速反馈，资料并未称其替代完整测试。
  • Backlog 是团队统一可信记录。official p.7 确认其维护优先级、WIP、状态、负责人及规格、设计、证据和历史；团队环与个人 IC 环在其间流转工作项和上下文。GitHub issues、wiki、PR、code 组成更大团队 Memory 仅为 recording 补充。
  • 团队环与个人环分离。团队环维护 backlog，个人环按“理解/Spec → Design → Agent 生成 → 验证”执行；最终审核关注各环节证据是否吻合。Daily report 汇总 PR 架构变化，再反向调整 Agent instruction；领域问题触发相应 DRI 参与。
  • AI 消除摩擦，也可能消除成长机会。准备工作减少的不只是重复劳动，还可能是新人理解系统细节、积累判断力的机会；节省的时间需重新投入系统健康、团队记忆和人的成长。

边界与联系

这是特定 Copilot 客户端团队的复盘，不代表微软所有团队，也不能证明 Agent 必然提效或必然损害质量。与 CodeWave 相同的是 Spec、验证和 Loop；微软额外突出了自动评分之外的架构 owner、DRI 和最终责任。

来源与待核｜official：李榕《当Vibe Coding撞上企业级现实-组织与人才视角》，22 页，pp.1–17 为主源；recording：微软Copilot团队企业级AI开发实践.pdf，pp.1–3，仅补客户端背景与问答。recording 的“去年”和人日均 30/200/900 PR 仍待核，不作效能结论。

AI 放大效应：生成加速，反馈与信任不同步

  • AI 复制并放大既有工程系统。Code Agent 会顺应并复制现有架构、代码习惯和规则，优点与腐化都会被放大；“100 倍”是讲者的强调性说法，不是本稿测算。
  • Harness 也会腐化。代码变化而文档、注释和规则不变，AI 会拿旧信息自信生成；模型升级后老限制可能变成绊脚石，补丁叠加也会遮蔽实际生效规则，因此规则要进入构建与机器检查。
  • 10 个 Agent 不等于快 10 倍。多个 Agent 仍可能排同一条构建、测试、真机反馈队列，并攒出未验证且互相冲突的改动；要压缩的是“改完 → 跑一遍 → 看结果”的完整一轮，现场目标是把这一轮压到分钟级。
  • 规模使影响面无法靠人脑维护。official 以 iOS 旗舰版为例：App 上的一个构建目标（Binary）包含 14.3 万 action，关键路径为 64 层串行编译；另页语境是一次干净构建的 10 个样本，不能外推为全部端或所有构建完全串行。
  • “九成以上”的对象已由 official 核清。约 400 人在一个仓里，其中九成以上在用 Code Agent；不是代码依赖比例，也不是员工用仓指标。

可信反馈是底数，AI 写 / 查 / 改是指数。影响面算得出、构建能复现、验证能自动跑，共同指向“能放心的交付速度”；这是工程方法论比喻，不是可直接计算的公式。

四大确定性底座：顺序不能乱

约束、定位、验证、度量合起来只回答“这个 MR 敢不敢直接合”；前一步没做，后一步只能靠猜。

底座回答的问题现场原则主要落地
约束什么能写？规则写进构建，机器来查强类型契约、依赖方向与语言规则；本地跑和 CI 一样的检查
定位该看哪里？让构建图划范围，别硬塞上下文查反向依赖、受影响模块 / 包 / 测试；重放失败 Action
验证凭什么说对？证明用户真的看见了Web DOM / 网络证据、后端真实接口、客户端运行证据
度量敢不敢合？只数直接能合的 MR以无人工返工的直接合入和实际交付价值替代 Token 等虚荣指标
约束 → 定位 → 验证 → 度量

约束与定位：规则进入构建，故障定位进入 Action

  • 契约、语言和工具链共同约束。RPC、跨语言与跨进程通信用强类型 IDL 描述，以统一协程替代 Callback，并通过 Bazel 全工具链密封让本地与 CI 一致；具体禁用清单不按 PDF 口述逐项扩写。
  • Chrome 示例纠正依赖方向。//chrome、//content、//base 分层，DEPS 声明可 include 谁，presubmit 的 checkdeps 拦截违规 include，跨进程先写 .mojom 再生成各端代码。正确方向是下层不许依赖上层，即 content 不得 include chrome，不是“上不依赖下”。
  • 本地与 CI 使用同一组检查。pipeline 覆盖 pre 分支落后检查、build 全配置编译、test 单测 / UI 测试、analysis 依赖边界与老问题、package 旗舰版 / 国际版出包、pin-align 跨仓契约版本对齐，让 Agent 尽早在本地拿到红灯。
  • 改契约后直接问构建图影响谁。构建图给出受影响模块、进入哪些包以及要跑哪些测试；首页卡片示例只纳入有依赖关系的双端、版本与测试，播放页和直播间无依赖则不必纳入。Web 侧可用 Turborepo 做同类依赖列举。
  • 构建挂了先重放失败 Action。找不到生成的 serializer 时，真实编译命令可能缺少 serialization 编译插件；正确修法是给 target 补构建插件，再重跑同一 Action 和受影响包，而不是乱改注解、import 或业务代码。照片支持 Bazel Query / aquery，不直接把“Meta Query / Action Query”当正式产品名。

验证与客户端瓶颈：编译绿不等于用户看见了

Web 用例的下游依赖用 mock，并固定账号和路由；APITest 走真实 HTTP 入口并断言返回含 badge，再开真浏览器按真实路由访问，用 CDP 断言页面 DOM 出现角标。一条用例留下四份证据：造的数据、接口返回、页面 DOM、网络和 Console，Agent 改完可自行重跑。

造带角标的卡片数据 → 真实 HTTP 接口断言 → 真浏览器 DOM 断言
  → 留存造数 / 接口返回 / 页面 DOM / 网络与 Console 证据

iOS 与 Android 的 UI 树、调试协议不同，真机、系统版本、账号和网络又引入变量；因此“编译过了、单测绿了”仍拿不出“用户看见了角标”的证据。CODEOWNER 不签，不一定是流程保守，而可能是证据不足；PDF 对原生编译、模拟器与虚拟化的判断不外推到所有客户端技术栈。

度量、合入信任与发布边界

现场实验完整漏斗：一个迭代 150 个全部需求 → 挑出 50 个最适合 AI 的 → < 5 个无人返工、直接合进主干。最后一项不是最终合入数，更不是通用 AI 成功率；需要补证据、改代码或重跑验证中的任何一样，都不计入。

改动类型（该实验口径）出错后如何撤回直接合并结果
后端实验开关、和界面无关的逻辑拨开关即可关闭，不用发版能直接合的全在这一类
只要涉及客户端的改动只能等下个版本，或者热修一个都没能直接合

直接合入与自动发布是两个权限边界。能直接合的改动首先具备快速撤回能力；客户端没有同类证据和撤回条件时，编译 / 单测通过仍不足以建立信任。

“六个 Agent，只留下一个”要拆开看状态：Code Agent 留下且是唯一全员铺开的；Debug 并入 Code Agent 成为工具；Verify 在建，用于补客户端“用户看见了”的证据；Deploy 仍属规划，目标是把证据接到线上并管理灰度、回滚；需求澄清与 Custom-code 被砍。

1.3REVIEW
LOOP

AI CR：从问题发现走向修复与追踪闭环

审查子环

定位｜腾讯音乐内部的 AICR 实践，以上下文工程、多轮采样和垂类 Agent 分工，推动问题发现、修复、增量验证与历史追踪形成闭环；闭环追踪和增量评审由两个 Agent 分工。

展开 / 收起技术档案

核心要点

  • 三类审查形态各有断点。直调 AI 简单但粗糙；IDE 审查前移了问题发现，却难以度量；流水线扫描能形成报告，后续仍靠人工标记修复。目标因此从“报问题”扩展到建议、验证和追踪。
  • Patch 先结构化，上下文按需扩展。系统对 Patch 解析、切片、分组并扩展变更前后内容；MCP 按需拉取需求文档、仓库文件和运行时数据，AST 用于调用结构与全局变量扫描，工具调用可见 fs.ast_global_check。
  • 业务上下文会改变风险定级。official 案例是歌房跳转使用硬编码 URL Scheme，而非设计要求的 openRoom(roomId) 桥接方法；结合需求、仓库上下文和动态读后判为高危、高置信。其他 App 名称仅为 recording-only。
  • 闭环追踪与增量评审是两个 Agent。前者追踪历史评审问题的修复状态并联动 GitLab/TAPD；后者在修复提交后立即扫描新增风险。部署失败后，CI/CD 另触发独立归因子 Agent，以变更文件清单和失败日志尾部做代码侧归因。
  • ACP 与 MCP 处在不同层。MCP 负责按需取数；ACP 把代码扫描、AI 单元、AI 智测和 AIops 串成闭链，统一接入／出口、上下文注入、结果归一与追踪；official 未展开其英文全称。
  • 指标必须分口径阅读。26Q3 的触达采纳率 46%、召回率 52%、覆盖率 99%、采纳问题数 12457 是不同序列，不能互算或合成准确率；部署修复标签为 1min，不补写“平均小于”。

关键机制

Patch 结构化 → MCP 按需补上下文 / AST 结构分析 → 通用与垂类审查 → 修复建议 → 闭环追踪 + 增量评审；部署归因是独立分支，ACP 再编排自动化节点。

边界与联系

资料没有给出自动通过、自动合入的门禁条件。与 B 站对照，AICR 的审查闭环仍需接可信验证与发布控制；与华为对照，两者都采用“机器扩展检查面、专门机制处理高风险判断”。

来源与待核｜official：李阳杰《从“能审”到“审出闭环”》，35 页，pp.6–19、25–31 为主源；recording 仅补口述。各指标分母、质量门禁统计口径，以及 recording 独有的 App 名、56% 与 35% 适用范围仍待核。

痛点材料给出的具体问题对研发范式的要求
效能提升与质量防护的 tradeoff代码产生速度不再是唯一瓶颈，“信任验证成本 > 代码编写成本”；非确定性代码及下游 MR 增多，使传统静态扫描和人工走读承压，可能出现“局部跑通、全局腐化”。把验证、架构风险和 DFX 防护前移，不能只提高出码速度。
单兵效能提升但组织效能卡顿单兵效能提升无法等价于组织级生产力提升，不同环节、角色的提效甚至可能相互抵消；代码产生效率提升 ≠ 需求交付时间缩短。重组角色、流程和交付关系，而非只替换个人编码工具。
日间算力不足、夜间算力闲置As-Is 是实时辅助时资源争抢、被动等待，低交互时段又出现资源闲置；日程只是资源争抢示意，不是利用率统计。将可延迟工作与实时辅助分开调度，利用离散的空闲容量。

从传统研发到 SDD：三重演进

  • 角色重塑——职责边界上移，AI 承接流水线作业。人类聚焦意图定义与终态校验，AI 深度接管标准化执行；研发重心从代码向意图跃迁，并不等于所有岗位已经消失。
  • 质量左移——设计即质量，验证即开发。PRR 与 DFX 验证全面左移至 Feature 设计阶段，使 DFX 成为设计阶段的自动化内驱力，而非事后补丁。
  • 时序重构——从串行执行到并行生产。规范驱动测试（SDT）消除开发与测试之间的 Gap，并激活 TDD 闭环；测试活动前移，原有先后顺序被打破。

幻灯片保留的关键作业流如下；FE 与 Story 为 1:1，测试活动同步前移。

Feature 设计（FE 与 Story 1:1；功能设计 + DFX 安全/可靠性/性能设计 + 一致性校验）
  → 方案评审 → 开发（编码 → 检视）

唯一 Spec、动态工作流、代码测试与 DFX

SpecX 的目标是把两端的人类判断转成 Agent 可执行、可验证的工程系统；SpecSpace 提供 AI 友好化的工程知识空间，SpecFlow 搭动态研发工作流，验证、门禁与反馈再回流。

SpecSpace（AI 友好化的工程知识空间）
  → SpecFlow（积木式搭建的动态研发工作流）
  → Eval / Gate / Feedback（验证、门禁与反馈回流）
  • 动态工作流不是固定流水线。计算、网络、存储等业务流与 DFX 等非功能要求做笛卡尔积组合，自动生成个性化工作流；内部已有 600 多个需求按此运行。该数字不等同于第四环试点交付数或全量推广范围。
  • 唯一 Spec 是跨角色协同锚点。中心仓维护唯一 Spec，由开发触发流程，设计、开发、测试三方会签锁定并联合验收；开发据同一份 Spec 生成代码，测试据此生成用例，使测试用例在代码输出前就绪（TPE）。
  • DFX 前移、按需供给并分层复核。PDF 称公司安全基线库约 2000 条规则，其中与华为云直接相关约 600 条，作为非功能要求强制落地；海量规范采用类似 Skill 的渐进式披露，按需加载到有限上下文，而不是全量塞入。代码提交后先由 AI 全面检视 DFX 合规性，疑似风险再交安全 SE 等人工专家把关。

人机形态材料中的含义与边界

合成作战与知识反馈

合成作战把串行交付改为并行协同。现场图以需求交付组为中心，由软件工程专家、工具/装备专家和质量防护等角色共同提供规格、工具、数据与能力支持，强调设计、开发、测试及工具装备并行作战，而不只是上游完成后交给下游。人员配比变化缺少完整统计口径，本稿不引用其数字。

Soft Trace 校准的是知识，而不只是代码。工程化追踪知识消费过程；人工反馈测试用例存在缺陷时，可反向定位并校准不准确的架构与业务知识。它与 AI 全量检查、人工复核疑似 DFX 风险共同构成反馈机制，但材料没有证明所有反馈已经自动闭环。

Spec / EARS 与文档解析

EARS 已纠正 PDF 的“AIRS”转写。它在需求入口消除歧义，而不是只换文档格式；模糊措辞、缺失触发条件、复合需求和不可验收的非功能描述分别改写。

原始问题传统描述EARS 化处理
模糊词“最好能”“方便一点”改为“应 / 必须”等可判断措辞
省略触发时机只说系统执行动作补“当……时”“若……”及可选前置条件
复合需求一句话混入多个要求拆成多条，并区分验证与提示
非功能需求不可验收“不能太慢”改成“2 秒内”等量化约束

自动保存示例被改写为“在编辑框中停止输入超过 5 秒时，系统应自动保存当前内容至草稿箱”。标准化由此暴露问题、形成 checklist，并统一验收与 Benchmark 输入。

Spec-first 不是 Spec 永远覆盖代码。团队比较过 Spec first、Spec as anchor、Spec as source，实践中以 Spec-first 为主；出现新需求时，再以代码为真实信源形成增量需求。持续同步、冲突优先级和版本治理仍待核。

原始文档解析是另一层需求工程。多模型、多策略组合切割与多页并行用于处理流程图、合并或跨页表格、多栏阅读顺序、Mermaid 与 UI 原型语义转换，并包含表格元素提取 / 替换和跨页单元格合并；未清晰复核的 OCR 组件不作猜测。

official 多处一致给出需求文档解析 73.6% → 95%，正文统一采用这一口径；recording 的约数仅为粗略转述，不再并列为另一组实验。数据集、样本量和评分细节仍待核。

Harness / Loop：前馈、反馈与分治

Guides（Feedforward）+ Sensors（Feedback）：Spec、执行计划和上下文管理主要提供事前软约束；Linter、Checker、TDD、Hooks，以及全局代码、规格符合性和代码质量 Review 形成事中、事后反馈。目标是事前可约束、事中可控制、事后可验证，而非只延长 Prompt。

长任务主要现象工程机制具体含义
验证不足、无测试或伪测试通过增强反馈控制、增加闭环测试、检查与 Review 形成“生成—报错—修正”循环
上下文受限、遗忘、遗漏或篡改需求分治思想大问题拆小，大环拆成小环和边，逐步夯实

需求拆解比较功能模块、领域边界和用户故事，但最终不是三选一，而是需求先按功能模块切，技术设计再按领域边界整合。

拆解方式相对优势主要风险 / 后续校准

  → 模块级并行生成与局部验证
  → 全链路检查及修复

自动化迭代平台、自我迭代与 Runner 边界

现场架构将 AI Benchmark 评测与全链路追踪平台标为 Stellibra（星衡），它整合数据集、执行、测试 / 评估、问题分析修复、可观测和自我迭代，而非只有评分表。

  • 数据集与执行：管理文本、图片、富文本文档、上下文环境 ZIP，支持预处理、筛选、版本与数据回流；整体应用和各阶段均可运行，并可从已有断点继续。
  • Runner 口径：架构列出 Local / API / Sandbox / Cloud Runner，但当前团队主要以 Local Runner 和 API Runner 为主，不能写成所有评测都在云端。
  • 测试、修复与观测：整体应用执行端到端测试并生成报告，阶段评估可下钻；QA 提单后可接入日志分析、Debug、经验回流、MR 等 Skills，但开发者 Review 后才合并。链路追踪记录 Prompt、输出、Token、延迟和评分。

自我迭代以自动执行、自动测评和智能修复为前提，控制策略如下。

每次只开发一个实验想法并提交 commit
  → 自动执行 + 评估得到分数
  → 分数提升，或能明显简化系统：保留 commit
  → 否则：reset 该提交
  → 记录实验笔记，避免重复研究；支持人工批注，再进入下一轮

  • 个人提效不等于团队交付提效。需求对齐、需求变化的影响判断和完整业务验收都需要相关角色共同参与；Agent 主导推进不等于取消人的范围确认、变更确认和结果验收。

云端执行：平台、常驻 Node 容器与授权边界

FaaS 交付平台与 Agent 执行服务分层。平台负责页面与 BFF、身份 / 权限 / 上下文、业务流程与产物校验、任务状态、正式产物及存储，通过 runId 启动并查询或回调结果。现场图中的执行服务是常驻 Node 容器：统一运行框架包含 Workflow / Manifest、Pi 执行器、工具授权、执行预算、工作区范围与结果校验；Coding Root 拆任务并指定范围，Worker 使用独立 worktree，补丁校验后再集成验证。

入口与沙箱边界分层。official 确认入口为 Web / Delivery Session、钉钉群／数字员工、Skill/CLI，执行服务为常驻 Node 容器；recording 的“独立沙箱”仍未说明粒度，不能写成每个任务或每仓独立沙箱，也不能反写成 official 证明无沙箱。

人工授权写进入口和运行链路。人补充事实、发起工作、确认与验收；平台检查权限、当前版本、幂等、Coding 预检与仓库占用，只有已获准任务与冻结输入进入可信运行入口。Workflow + Agent Manifest 限定角色、工具权限、预算和输出契约，扩大修复范围也必须请人确认；构建、部署和测试闭环不证明系统拥有自动生产发布权。

多仓并行、Worker 隔离与条件恢复

交付共识分发到各仓独立执行，仓内主 Agent 再拆 Worker 子任务；Worker 使用独立工作树和文件范围，经过校验、集成、最终代码检查与提交回传，回执绑定代码指纹。平台与钉钉可查询进度，但开发并行不代表后续所有环节都并行。

交付共识
  → 仓库 A / B / C 独立 Coding
  → 仓内 Root 拆任务、指定范围
  → Worker 独立 worktree 与文件范围
  → 补丁校验 → 集成验证 → 最终检查 → 提交与代码指纹回执

失败续做有恢复条件。现场例子中，已合入主工作目录的页面成果保留，超时子任务的改动补丁自动保存；续做时从主工作目录创建新目录，再接回补丁并在原文件范围内继续。只有“可恢复且时间足够”才由主 Agent 发起续做，不能承诺超时后必然无损恢复。

测试闭环、串行修复与视觉验收

测试 Agent 在开发完成、部署就绪后执行自动化测试并提交带详细描述的 Bug；交付大脑对照证据分析，信息不足则补证据，需要人处理则明确负责人和动作，可自动修复才进入修改、验证与合回。PDF 另称部署后自动触发真机测试，现场流程图本身使用更宽泛的“自动化测试”。

开发完成 / 部署就绪
  → 测试 Agent 自动化测试并提交 Bug
  → 交付大脑对照证据分析
  → 补充证据 / 人工处理 / 自动修复分流
  → 修复版本复测原 Bug
  → 通过才关单；未通过则重开原 Bug

修复前必须先分析影响、明确范围；复测与关单 / 重开构成验证闭环。

多仓 Coding 并行，Bug 增量修复刻意先串行。official 以开发分支为基线，Bug A/B 各自新建修复分支并依次合回。理由是并行易互相影响、重复验证，Bug 量不大、并行收益有限，先串行可简化调度与合并；不是把 Bug 间依赖列为理由。

开发分支基线
  → Bug A 独立修复分支 → 验证 → 合回
  → Bug B 基于已含 A 的代码新建修复分支 → 验证 → 合回
  → 形成包含 A+B 的代码；每次修复保留独立记录

复杂设计稿还原分设计补查、编码校验、视觉验收。先整页再分区域补查，设计 Agent 补交互说明；编码时看图理解布局并读取样式属性，完成后以同一版设计稿对比真机截图。Figma 节点关联、字号 / 圆角比对与提交修复属于 PDF 补充；视觉验收不等同完整业务验收。

长任务预算与交互形态

长任务同时管理工作预算、整理预算和失败产物：设置工具轮次与总时长，划分工作和整理时间；接近上限提醒收尾，达到上限停止新工具调用、等待或取消当前操作，整理结论和未完成事项，收尾阶段也监控整理时长。成果完整且通过检查才继续，否则保留成果并说明原因；任一超时也返回已有成果与超时原因。

示例配置不是固定默认值。PDF 摘要举过 50 轮、10 分钟、耗时 80%提醒收尾；现场图只确认轮次 / 总时长预算、接近上限收尾和失败产物保留，三个数字不能写成已确认的固定默认值。

交互从不断增加 GUI 流程节点和按钮，转为以 LUI 对话为主线；当前界面主要用于呈现状态、共识与产物，也适配钉钉和数字员工协作。

核心要点

  • 自主进化只改非模型资产，并仍在进行中。official 的范围是 Prompt／Skill／知识／策略，不动模型；候选按断言与 Case 通过率回放，退化即拦，通过后灰度，异常秒级回滚。统一托管已落地，持续进化进行中，自治运维是未来；候选依据与退化明细仅为 recording 补充。
  • 知识入库先过三道校验。official 主文为权限、脱敏、质量，以断言审计和人工评审把关；时效性与冲突校验仅为 recording-only。

BOUNDARY

沙箱：用五类边界同时处理安全、状态与成本

执行隔离

定位｜official 将系统命名为 ARCA。沙箱围绕动作、网络、状态、身份和资源五类边界，支撑 Agent 托管、训练环境供应和高危动作执行。

展开 / 收起技术档案

核心要点

  • 动作边界限制爆炸半径。策略中心按查询、代码执行等风险分类，决定在 Agent Host 直接执行、进入沙箱，还是人工审批后执行；高危动作的受控边界落在入口和出口网关。
  • 网络边界不能一刀切。最初 untrust 区只允许访问外网，内部办公 Agent 因而无法使用；后续增加办公区，允许访问内部办公服务，所有出口统一经网关管控。边界应匹配业务，不是越严越好。
  • 状态外置支撑“常驻感”与实例可回收。进程内存可销毁重建，workspace、依赖和产物进入持久化文件存储并跨实例挂载；A 沙箱销毁后，B 沙箱可按 ID 重新挂载结果。快照/Restore、空闲回收和缓存池用于兼顾体验与成本。
  • 身份从沙箱剥离并全程归因。official 主文为短期委托身份、最小权限 token、唯一身份验签、目标白名单与 trace id 全链路审计；OSS AK/SK 平台托管、占位符与出口注入仅为 recording 实例。
  • 批量环境供给是另一套资源问题。RL 场景依赖镜像加速、节点缓存命中、快照批量 Fork、调度、配额和公共链路隔离；环境交付拆成资源准备、调度、挂载、启动、就绪五阶段观测，避免算力等待环境。
  • 系统 Skill 的只读要在挂载层保证。root 可绕过 555，导致同一业务多个共享 NAS 目录的沙箱加载被改 Skill；修复是沙箱侧 ro 挂载、内核以 EROFS 拒绝写请求，业务侧仅管控平台保留 rw 发布链路。

数字口径

official 给出百毫秒级创建、日均业务创建沙箱 100w+、处理亿级沙箱请求、100% 访问审计覆盖。某业务从预热池切到缓存池后的实测资源成本 −96%，不是启动时延下降 96%，也不是统一收益。recording 的约 50ms 与已有 standby 取出后 20–30ms 交付只作口述补充，池尽仍走冷启动；各启动数字不可拼接。

边界与联系

“永远在线”是体验目标，连续性来自状态外置和恢复。official 明确 CRIU 全量快照大、镜像升级可能不兼容、连接会短暂中断；快照不等于外部连接和分布式事务的一致恢复。缓存池按模板维护少量就绪沙箱，命中直接分配、用一个补一个，未命中走冷启动。

来源与待核｜official：林鑫《从沙箱到执行边界》，37 页，pp.6–17、20–24、27–30、34 为主源；recording pp.1–5 仅补 20–30ms、约 50ms、池规模背景与 AK/SK 注入。96% 成本项、统计窗口与各启动测试条件仍待核。

展开 / 收起技术档案

公司级痛点与治理输入

  • 规模化把单点缺陷变成系统风险。official 给出 26Q2 业务 Agent 应用数 10000+；25Q3→26Q2，AI 代码生成占比 30%→60%、生成行数 1000w→4800w。单次任务消耗可超预算 10 倍，调查中 78% 的业务没有评测基线；这些不是统一提效指标。

五层技术栈：Agent 是服务单元，治理横切全局

五层从模型供给一路延伸到治理脚手架；传统网关、服务、存储与容器仍保留，并新增 AI 安全、Agent 智能、AI 引擎和模型／GPU-NPU 供给。

Agent 是 AI 架构的核心服务，Multi-Agent 对应 AI 时代的多服务架构；注册、路由、鉴权、可观测和 SLA 因而要扩展到 Agent，而不是被新架构取消。

模型只位于技术栈底部；能否进入生产还取决于工具、Agent、治理，以及横切的安全、成本、稳定与组织机制。

Multi-Agent：先统一身份语义，再谈互通

  • 先统一 Agent 定义。Agent = LLM + Tools + Autonomous Loop；单次 Prompt、Skill、MCP Server、CLI 和仅检索后单次回答的 RAG 不自动成为 Agent。治理对象统计由 5w+ 收敛为 1w+，首先是定义口径变化，不能解释为应用缩减。
  • 分类服务于差异化治理。对公司约 1 万 Agent 按部署模式、能力范围、身份视角和开发模式分类，使不同 Agent 适用不同身份、授权与安全策略。
  • 身份连续回答四个问题：Agent 是谁、代表谁、能做什么、做过什么。真实 Case 中，统一身份认证与一次授权全链路透传后，跨 Agent 调用成功率不足 60%→99% 以上；不能外推为所有调用。

CLI 与 Skill：标准化能力供给

  • CLI 面向本地编码和自动化执行；official 给出改造后 CLI 标准化调用覆盖率 >99%，但分母、统计周期和业务范围未给。
  • Skill 封装原子能力或固定工作流；面对 10+ 市场、1w+ Skill，治理重点是 Manifest、目录、命名、文档／描述、安全强约束和可观测规范，而非只增加市场数量。
  • MCP 与 A2A 不能互相替代。MCP 统一接入外部工具与数据，A2A 面向自治 Agent 间通信协同；CLI、Skill、MCP、A2A 应在 Multi-Agent 架构中各归其位。

Harness 门禁与交付验证

  • 公司基础规范 + 业务继承扩展。公司级规范覆盖命名、分层、接口契约、日志、异常和安全编码；限流、熔断、降级、超时、重试等兜底逻辑必须有单测，接入脚手架统一对接 RPC／OpenAPI／Hive／Kafka／KDB／Redis，上线门槛为准入＋准出＋自动化测试三道闸，目标是守住质量下限。
  • 门禁规则真正进入业务 Harness。四组规则覆盖组件标准化、架构与业务规约、稳定性／性能／安全、Agent 使用；幻灯片给出 18 个评测、197 条规则、1806 个测试用例，覆盖度与通过率均 100%，这里的 100% 只指门禁自身评测，不等于 AI 代码正确率。
  • 从拦截转向治理。发现 1157、已治理 162，80% 是治理率目标而非当前值；已治理 162 个中 14% 由 AI 辅助直接解决，分母不是 1157。另有 375/2500 工程师与 7/13 Harness 业务覆盖，保留分数形式。
PRD → Coding（规范约束）→ Test（可测性）→ Check（可验收）→ Deploy（DevOps/AI 友好）→ 反馈
功能验证完整包括 API／RPC 接口测试、Task 触发、消息收发、监控与日志；能编译、能部署、能验证才构成交付。

优先级：四档是投入排序，不是完成度

共性优先、底线优先、价值可量化之后，再配置后续投入。已有门禁、安全或 CLI 成果与档位并不矛盾；长期储备被描述为面向未来 2–3 年的能力建设。

Auth、Storage、Edge Function 等组件 Serverless 化，DB 则通过自研存算分离架构实现 Serverless；目标是同时处理低峰空耗与突发扩容，而非只解决“能部署”。

Sandbox：隔离执行环境与 Agent Runtime

从 API 到隔离 MicroVM，方案分为微服务、控制、执行、资源四层。

层级主要组件与关系

  • Agent in Sandbox：Agent 自身运行在隔离沙箱中，在受控计算、网络、文件和工具权限内执行任务。
  • Agent call Sandbox：Agent 按任务动态调用沙箱，平台负责调度、权限校验、资源限制和结果回传。

Dual Loop：内环优化能力，外环校准方向

  • 内环是 Agent 能力闭环，关注意图识别、指令遵循、Badcase 率；外环是业务指标闭环，关注外呼触达率、配对率、ROI。外环通过业务归因定义 Badcase，决定内环下一轮优化什么。
  • 只看内环可能在错误方向上越做越好。现场“能力上升、触达下降”只是趋势示意，根因示例是圈选未命中高意向司机，不能当作已披露实测降幅。
  • 定时 Loop ≠ Dual Loop。定时触发本身不会自动产生业务归因或方向校正。

→ LLM Judge 按专家标准评分 → Badcase 分布与归因
→ Prompt / 策略优化 → 下一轮迭代

金牌话术萃取：专家经验 + 真实对话
→ LLM 萃取表达结构、异议处理与策略 → Gold Strategy
→ 回灌 Prompt / 策略 → 线上业务指标验证

展开 / 收起技术档案

材料口径：同场互校，不是独立实验证据

现场照片用于确认幻灯片术语、图示和表格，同场 AI 摘要用于补充未拍到的讲述与问答；二者只能互校，不能当成两份独立实验证据。同页复拍不重复计数，PDF 独有说法降级为“问答摘要称”。

MemOS：从检索记忆扩展为记忆操作系统

  • 功能链不只是检索：记忆抽取 → 记忆组织 → 记忆检索 → 记忆更新 → 记忆共享，覆盖关键信息抽取、逻辑与时间组织、历史调用、过时记忆修正和跨任务 / 跨个体复用；抽取与更新处均标出幻觉风险。
  • PDF 的五环节是另一种工程视角：信息抽取 → 组织存储 → 检索应用 → 组装调度 → 上层系统接入，调度兼顾检索上下文带来的 TTFT 与准确度。处理接入流程与系统能力链不强行一一对应。
MemOS 层次现场可确认的组件与职责

这套范围明显大于向量数据库或 RAG 召回器。向量与图的取舍仍只来自 PDF：资料所述实验中图数据库提升通常不超过 5%，且增加工程复杂度；不能推广成“图记忆普遍无效”。性能页也缺少完整硬件、负载、对照版本和统计窗口，不据此做跨产品排名。

Reflect2Evolve：把执行过程加工成可复用能力

Agent 记忆还要记“做过什么、为什么、哪里错了、如何纠正”。代码修改、命令、工具输出、子 Agent 结果、日志、反思与用户反馈形成 grounded trace；目标不是延长历史，而是把过程转成能力。

Value Backfill 分配步骤价值。任务级用户反馈提供终局奖励锚点，步级反思向历史步骤回溯价值 V，用于检索排序、跨任务策略归纳、决策修复和 Skill 结晶；高价值内容可能是中间根因定位或纠错步骤，而非只有最终成功结果。

执行时的分层调用提供什么典型检索或注入方式
Tier 1 · Skill可执行的策略骨架匹配 trigger / scope 后注入 procedure、verification、scope 与 anti-pattern。
Tier 2 · Trace / Episode成功或失败步骤的操作细节以 error signature、embedding、结构 / 语义匹配与 V 排序，回填 command、patch、fallback。

Skill：治理式升格，而非直接蒸馏嘈杂轨迹

  1. L1 证据：保留步级 trace，并用终局反馈回填 V。
  2. L2 策略：至少两个 Episode 支撑，才归纳触发、流程、校验和边界。
  3. 双门控：既要有证据且 G > 0，又要求触发、流程和边界稳定。
  4. Skill 卡：通过确定性校验才可调用，并携带 schema、证据与工具白名单。
  5. 生命周期：以 η = (n_pass + 1) / (n_trial + 2) 和 G = V̄_with − V̄_without 驱动激活、归档与退役重建；幻灯片示例为 η ≥ 0.6 激活、η < 0.2 归档，持续负增益则退役重建。

PHASE-Tree：维护“现在的角色状态”

它解决的是 stale-state failure，而非事实召回失败：即使记得日期、地点和事件，角色口吻、关系边界与情绪仍可能停在初识阶段。PHASE-Tree 把“发生过什么”转换为“经历之后，现在是谁在说话”。

Deep Swarm：把容量 RCA 组织成分支调查与证据回归

SRE / RCA

定位｜将容量根因分析组织成“观测证据压缩 → Session Tree 并行假设验证 → 精简交接 → 金标回归”的调查流程，目标是在可控时延内给出带证据、可人工接管的候选根因。

展开 / 收起技术档案

核心要点

  • 先选边界相对清晰的容量场景。痛点包括海量 Metric/Log/Trace 和变更数据、长程调查被错误线索带偏，以及线上故障时效；首个场景聚焦流量、性能、依赖、资源四个方向，而非一开始覆盖全部故障。
  • 上下文处理先改变证据形态。时序数据围绕变点动态分段，提取中位数、斜率、方差等特征，同时保留变点前后原始值供复核；Trace 在异常窗口内分别采样失败、慢请求和正常请求，避免只把原始海量数据塞给模型。
  • Session Tree 隔离调查路径。每个 Entry 保存历史并通过父指针成树；Worker 将共享事实前缀、自身任务和工具调用组合后并行调查。分支结束只向主分支返回关键结论、证据引用和未解决问题，减少已否定方向对后续判断的污染。
  • 固定步骤工具化，低价值分支可提前终止。高频固定流程封装为单一 Tool 减少模型往返；当现有结果足以解释异常且无反证时，可取消其余分支，同时保留未完成状态供人工继续。交付面板呈现根因、证据和受影响服务拓扑。
  • 评估同时看根因和证据。评测从真实告警出发，由 LLM Judge 对根因和证据逐项语义匹配，再由程序计分；金标由 Agent 起草、人工核对后入库，证据匹配用于改进流程，不是根因命中的刚性门槛。资料称在 100 多个内部金标用例上回归准确率约 70%，但未明确对应哪个具体指标。
  • Bad Case 修复可能需要补领域机制，而非只改 Prompt。资料以 Circle 扩列漏判为例，补充领域知识，并区分扩列操作与实际切流时间戳，说明数据语义本身也会成为根因分析能力的一部分。

关键机制

原始观测 → 带时间窗的证据压缩 → 公共事实与独立假设 → Worker 并行调查 → 精简 join/提前终止 → 根因、证据与未决问题 → 金标回归

边界与联系

共享事实是本轮调查中供分支复用的模型上下文，不等于人工核对后的金标事实。约 70%、首个假设约 90 秒和完整诊断平均 3 分多钟均是内部口径，不能外推到全部故障。与电商相同，重点是保留任务所需结构；与 Mira 相同，自动动作需要证据、状态和人工接管点。

来源与待核｜无可靠同场 official（no_official）。仅 recording：Deep Swarm 容量根因分析 Agent 设计与落地分享_summary.pdf，pp.1–5；不借相似 SRE／AgentOps official 补证。待核SEA1/SEA2、LensCancel、Circle/扩列 的正式术语；约 70% 的指标对应、金标场景分布和时间范围。

EVOLUTION

电商导购 Agent：多业务域架构与受门禁约束的自进化

电商导购

定位｜快手电商案例把导购 Agent 的稳定性拆成多业务域契约、Task Context、三路 Memory、轨迹评测和受门禁约束的 Bad Case 修复；核心认识是“离线修好”不等于“C 端上线无损伤”。

展开 / 收起技术档案

核心要点

  • 跨域与长对话叠加放大状态管理问题。一次购物 Query 可能经过导购、营销和履约域，覆盖售前、售中、售后；资料称成交用户平均对话超过 30 轮，需求和任务状态持续切换，仅靠内部对话历史不足以理解用户。
  • 架构从 Workflow 到单 Agent，再到 Sub-Agent as Tool。预定义子图 Workflow 演进到单 Agent Loop 后，工具与策略汇入又造成上下文膨胀、边界模糊和归因困难；售后、营销因此被拆成 Sub-Agent。每个 Sub-Agent 需要独立评测集、交付标准和显式上下文契约。
  • Task Context 独立于普通历史压缩。原始 Query、对比商品、任务进度等关键状态被显式定义，不随滑动窗口或一般 Summary 一起压缩；每轮后更新 Summary，下一轮前重新注入。历史 Summary 与 Task Context 还使用面向不同任务微调的小模型。
  • Memory 分离线、进线、在线三路。离线从购买、浏览、直播行为提取固定型用户特征；进线采集进入对话前的商品浏览、加购等行为；在线由模型通过 Memory-write Tool 实时写入。存储采用“用户—类目—商品”行为图谱；对话时全量加载的是用户特征与近期进线行为，订单搜索、购物车检索、类目偏好等高开销查询则封装为 Tool 按需调用。
  • 评估由轨迹、单点能力和上线回归组成。自研兼容 OpenTelemetry 的采集链路，Memory 与 Tool 有独立评测；上线采用基线集与线上回归集双轨，前者观察整体水位，后者覆盖高频和安全敏感问题，要求基线波动可接受且回归集通过。
  • 自进化采用受约束归因和分级修改权限。Bad Case 经组件分类、多阶段下钻和归因合并后，Codex 在独立容器云分支修改并留痕；Prompt 与 Tool Description 可自动修改和评测，Context 与 Memory 管理策略则必须人工审查，线上 AB 无负向波动后才发布。

关键机制

Bad Case 筛选 → 受组件约束的归因 → 沙箱分支修改 → 独立 Bad Case 集验证且整体基线不退化 → 特定策略人工审查 → 线上 AB → 发布

边界与联系

AB 是最终线上门禁，不是完整评估体系；“无负向波动”也不自动等于长期正向收益。过细 Prompt 修补会膨胀上下文、拉长 RT，并可能影响 GMV，所以离线提升不能直接换取上线资格。自动修复能力也分类受限：工程 Bug 较易自动修复，Prompt/Tool 需多轮收敛，Memory 加工策略因证据链缺失仍难自动修复。与 Deep Swarm 都强调按需注入事实，与 Mira 都限制自动修改权限。

来源与待核｜无可靠同场 official（no_official）。仅 recording：电商导购Agent架构演进与自进化实践分享_summary.pdf，pp.1–5；不借相似电商、导购或广告 official 补证。待核Pi 模型、Memory L、ILCP 的正式名称；“去年/今年初”的相对时间、30 轮统计窗口、AB 样本量/周期/显著性和 GMV 影响幅度。

腾讯游戏测开：视觉执行与开发 Agent 分层

游戏测试

定位｜不是让视觉模型独立理解并验收整个游戏，而是由上层开发 Agent 编排业务脚本、状态和断言，底层小视觉模型负责 PC 操作，再以程序校验和结构化人工卡片控制系统性错误。

展开 / 收起技术档案

核心要点

  • 业务约束决定折中架构。资料称大型竞技游戏版本迭代快、测试用例多；纯脚本容易受坐标和颜色变化影响。完全交给视觉模型又缺乏控制。风格化 UI 的抽象符号和业务背景也难以被通用 VLM 直接理解。
  • 视觉执行 Agent 与开发 Agent 分层。小视觉模型在测试机上执行操作；开发 Agent 以脚本注入业务知识、状态逻辑并负责探索、调试；后续增加分配设备账号的运维 Agent 和负责汇报、发起任务的主 Agent。
  • 上下文保留完整操作前后状态。系统保存 pre/post/update 画面、账号前置状态和游戏状态日志，而非只保留按钮局部截图；第一批高精度数据 Demo 由人工构建，用完整证据约束产物并减少扫盘幻觉。
  • 保护性断言与业务断言分层。前者保证步骤推进，后者负责真正验收。交付前自动构造正反例并重复运行，避免鼠标悬停高亮等假阳性。session 和任务结束还会运行脚本检查程序逻辑，不合格则打回。
  • 人工从持续巡查转为批量处理决策卡片。Agent 拿不准时尽早进入 Human-in-the-loop；卡片汇总目的、观察结果、已尝试内容和原文所称的“回想方向”，由人工统一决策，避免错误思考在系统内反复回响，也减少人工反复回复“继续”。
  • 视觉操作不妨碍非视觉数据校验。界面执行依赖截图，但开发 Agent 可编排固定脚本查询前端接口、触发操作，并核验前后端接口和数据库变化；审美类问题则只由 AI 提取疑似区域，再交人工二次检查。

关键机制

人工需求/用例 → 主 Agent 派发 → 开发 Agent 探索与调试 → 运维分配设备账号 → 视觉端执行 → 前后状态/日志证据 → 程序检查与分层断言 → 必要的人工卡片决策

边界与联系

正反例数量和重复次数未给出，“无方差通过”是该系统的交付准则，不等于证明所有真实场景都无假阳性。经验生成速度也可能超过人工审核能力，因此自动沉淀不等于自动可信。讲者所称“框架仅适用未来 3–6 个月”是预测，不是已验证生命周期。

来源与待核｜无可靠同场 official（no_official）。仅 recording：腾讯游戏测开团队基于视觉模型构建自动化测试 Agent 系统分享_summary.pdf，pp.1–3；不借相似 GUI／游戏研发 official 补证。待核“20–30 个并行 Agent”的详细拓扑；“每日/每周”“开发/处理”“50 套决策”等口径差异；“回想方向”等原词。
